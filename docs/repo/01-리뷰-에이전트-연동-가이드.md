# 리뷰 에이전트 연동 가이드

## 현재 상태

`code-fix-agent`는 HTTP API와 JSON 파일로 리뷰 이벤트를 받는다. `code-review-agent`에는 자동 전송 기능을 연결하지 않았다. 다른 저장소를 변경해야 하는 자동 연동 작업은 대상 파일과 영향을 설명하고 사용자 승인을 받은 뒤 진행한다.

현재 사용할 수 있는 방식은 두 가지다.

- `fix-agent submit`: 같은 장비의 리뷰 도구가 JSON 파일을 직접 등록. 수신 token 불필요
- `POST /reviews`: 다른 프로세스나 장비에서 Bearer token으로 이벤트 전송

두 입력은 같은 SQLite 작업 큐와 수정 절차를 사용한다.

실제 이벤트를 등록하면 finding마다 최신 원격 target을 기준으로 별도 worktree를 만들고, 조건을 통과한 변경만 설정된 remote로 push한다. 개발·검증 환경에서는 사용자가 대상 저장소 실행을 승인한 뒤 이벤트를 등록한다.

## 설치와 설정

```bash
cd /Users/brokenclaw/hermes-workspace/code-fix-agent
python3 -m venv .venv
.venv/bin/python -m pip install -e .
```

저장소에 포함된 `fix-agent.toml`은 다음 대상을 등록한다.

| ID | GitHub 저장소 | remote/target | 반영 방식 |
|---|---|---|---|
| `matrix-mobile-v2` | `inswave/Matrix_Mobile_V2` | `origin/dev` | direct |
| `testsquare-fable` | `inswave/TestSquare-Fable` | `origin/dev` | direct |

다른 대상을 추가할 때는 `fix-agent.example.toml`을 복사한다.

```bash
cp fix-agent.example.toml fix-agent.local.toml
chmod 600 fix-agent.local.toml
```

설정 파일에는 비밀값 대신 환경 변수 이름을 적는다. HTTP 서버를 실행할 때는 수신 token과 저장소별 쓰기 token을 설정한다.

```bash
export CODE_FIX_TOKEN='replace-with-a-secret'
export MATRIX_MOBILE_FIX_GITHUB_TOKEN='repository-scoped-token'
export TESTSQUARE_FABLE_FIX_GITHUB_TOKEN='repository-scoped-token'

.venv/bin/fix-agent serve --config fix-agent.toml
```

GitHub token은 대상 저장소 clone·fetch·push와 PR 방식의 PR 생성에 필요한 범위만 부여한다. Codex와 테스트 명령에서는 token, secret, password와 webhook 환경 변수를 제거하며 Git network 명령과 `gh pr` 명령에만 저장소 token을 전달한다.

`CODE_FIX_TOKEN`은 HTTP 요청 인증에만 쓴다. 같은 장비에서 `fix-agent submit`을 호출하면 이 token이 필요 없다. 저장소별 GitHub token은 별개다. 현재 구현은 push 전에 `github_token_env` 값을 확인하므로 로컬 CLI 방식에서도 GitHub 인증은 생략할 수 없다.

## Discord 작업 알림

웹훅 주소는 저장소별 `[repositories.discord]`에서 지정한다. 저장소에 포함된 `fix-agent.toml`은 실수로 메시지를 보내지 않도록 둘 다 꺼져 있다.

```toml
[repositories.discord]
enabled = true
webhook_url_env = "MATRIX_MOBILE_FIX_DISCORD_WEBHOOK_URL"
timeout_seconds = 30
```

`webhook_url_env`는 주소가 아니라 주소를 담을 환경 변수 이름이다. 실제 값은 프로세스를 시작하는 shell에 넣는다.

```bash
export MATRIX_MOBILE_FIX_DISCORD_WEBHOOK_URL='https://discord.com/api/webhooks/...'
export TESTSQUARE_FABLE_FIX_DISCORD_WEBHOOK_URL='https://discord.com/api/webhooks/...'
```

Discord 기본 웹훅에는 별도 token이 필요 없다. Discord 호환 중계 서버가 Bearer 인증을 요구할 때만 `webhook_token_env = "..."`를 추가하고 그 환경 변수를 설정한다. `webhook_url = "https://..."`로 주소를 직접 적을 수도 있지만, 비밀값이 설정 파일과 Git 기록에 남을 수 있으므로 환경 변수 방식을 권장한다. `webhook_url`과 `webhook_url_env`를 함께 쓰면 설정 오류로 중단한다.

알림 대상은 정책 제외, target 이동, merge 충돌 감지·해결, push 완료, worktree 정리 실패와 작업의 `completed`·`rejected`·`failed` 상태다. 내부 진행 이벤트는 커서만 넘기고 전송하지 않는다. 웹훅 실패는 수정 작업 상태를 바꾸지 않는다. 실패 event ID, 횟수, 원인과 다음 재시도 시각을 `discord_cursors`에 남기고 5초, 30초, 2분, 10분 간격으로 재시도한다.

worker가 실행 중이면 재시도도 자동으로 처리한다. 직접 확인하거나 저장된 대기 시간을 무시하고 다시 보낼 때는 다음 명령을 쓴다.

```bash
.venv/bin/fix-agent notify-once --config fix-agent.toml
.venv/bin/fix-agent notify-once --config fix-agent.toml --force
```

처음 알림을 활성화하면 기존 event의 마지막 ID에 커서를 맞춰 과거 알림을 한꺼번에 보내지 않는다. 이후 생성된 event는 HTTP 2xx 응답을 받은 뒤에만 커서를 전진한다. 전송이 실제로 성공했지만 응답 확인에 실패한 경우 같은 event가 다시 갈 수 있으므로 Discord embed의 `Event ID`로 중복을 확인한다.

## 리뷰 이벤트 계약

`POST /reviews` 요청은 `Content-Type: application/json`을 사용하며 `Authorization: Bearer <CODE_FIX_TOKEN>`이 필요하다. 본문 형식은 `version = 1`이다.

필드 제약, fingerprint 생성법, 성공·오류 응답, 재시도와 버전 호환 규칙은 [리뷰 이벤트 v1 계약](02-리뷰-이벤트-v1-계약.md)을 기준으로 삼는다.

```json
{
  "version": 1,
  "repository": "inswave/Matrix_Mobile_V2",
  "branch": "dev",
  "baseline": "0123456789abcdef0123456789abcdef01234567",
  "target": "123456789abcdef0123456789abcdef012345678",
  "findings": [
    {
      "fingerprint": "sha256:54e4c2451c58e7dd7132565aa3f2153884e53b3c89aed1f54e63136b40c787b2",
      "severity": "Major",
      "commit": "123456789abcdef0123456789abcdef012345678",
      "file": "client/example/File.kt",
      "line": 42,
      "cause": "구체적인 실패 조건과 영향",
      "solution": "검증 가능한 수정 방법"
    }
  ]
}
```

각 commit ID는 40자리 또는 64자리 전체 object ID여야 한다. `file`은 저장소 상대 경로를 사용하고 `fingerprint`는 `sha256:` 뒤에 64자리 소문자 16진수를 붙인다. 하나의 이벤트에 finding을 한 개 이상 넣어야 한다.

HTTP 전송 예시는 다음과 같다.

```bash
curl --request POST http://127.0.0.1:7081/reviews \
  --header "Authorization: Bearer ${CODE_FIX_TOKEN}" \
  --header 'Content-Type: application/json' \
  --data @review-event.json
```

서버는 계약과 저장소 allowlist를 확인한 뒤 `202 Accepted`를 반환한다. 같은 저장소·branch·fingerprint 조합은 다시 등록하지 않는다.

## JSON 파일 직접 등록

서버와 수신 token 없이 이벤트를 큐에 넣고 작업 한 건을 처리할 수 있다. 송신 프로젝트는 설치된 `fix-agent` 실행 파일, 이 프로젝트의 설정 파일, 자신이 생성한 이벤트 파일만 사용한다. `code-fix-agent` 저장소 파일을 직접 수정하지 않는다.

```bash
.venv/bin/fix-agent submit \
  --config fix-agent.toml \
  --file review-event.json \
  --run-now
```

등록과 실행을 나누려면 `--run-now`를 생략한 뒤 다음 명령을 사용한다.

```bash
.venv/bin/fix-agent run-once --config fix-agent.toml
```

`--run-now`와 `run-once`는 호출할 때마다 대기 작업을 최대 한 건 처리한다. 여러 finding을 한 이벤트에 담고 상시 worker를 실행하지 않는다면 `no queued jobs`가 나올 때까지 `run-once`를 반복하거나, finding 하나당 이벤트 하나를 순차 등록한다.

## 처리 절차

1. 저장소, branch, severity, fingerprint와 finding 경로를 정책으로 검사한다.
2. `local_path`가 없으면 GitHub 저장소를 `--no-checkout`으로 clone한다. 있으면 기존 Git 저장소를 사용한다.
3. `remote/target_branch`를 fetch하고 최신 commit을 구한다. 리뷰의 `target`이 최신 target의 조상이 아니면 중단한다.
4. 최신 target에서 detached worktree를 만들고 도입 commit과 finding line이 `baseline..target` 변경에 속하는지 확인한다.
5. read-only Codex가 실제 실패 경로를 다시 검증하고 `precheck_reason`을 기록한다.
6. 유효한 finding만 worktree에서 수정한다. Codex는 적용 범위의 `AGENTS.md`와 `additional_instructions`를 따른다.
7. 변경 경로와 크기 정책, 저장소 하네스, read-only 수정 결과 검증을 차례로 통과한다.
8. 수정 commit을 만든 뒤 원격 target을 다시 fetch한다.
9. 원격이 이동했으면 최신 target을 worktree에 merge한다. 충돌은 별도 Codex가 해결 사유를 남기며, 정책·하네스·결과 검증을 다시 실행한다.
10. 검증 중 target이 다시 이동하면 `max_remote_merge_attempts` 범위에서 merge와 재검증을 반복한다.
11. `direct`는 작업 commit을 `remote/target_branch`로 push한다. `pull_request`는 `autofix/<repository-id>/<fingerprint-short>`로 push한 뒤 PR을 만든다.
12. push 뒤 worktree를 강제 제거하고 임시 디렉터리 삭제와 `git worktree prune`을 수행한다.

finding 하나가 SQLite 작업, worktree, fix commit과 push의 단위다. 사실 검증이나 merge 후 재검증이 실패하면 push하지 않는다. 상세 명령과 정리 조건은 [수정 작업과 worktree 생명주기](03-수정-작업과-worktree-생명주기.md)에 정리했다.

## 상태와 판단 기록

상태는 `state_dir/jobs.db`에 저장한다.

```bash
.venv/bin/fix-agent jobs --config fix-agent.toml --json
.venv/bin/fix-agent events --config fix-agent.toml --job-id 41 --json
.venv/bin/fix-agent events --config fix-agent.toml --after-id 120 --json
```

| 상태 | 의미 |
|---|---|
| `skipped` | severity, 경로 또는 fingerprint 예외로 처리 제외 |
| `queued` | 처리 대기 |
| `validating` | finding 사실 여부 확인 중 |
| `fixing` | 사실 검증을 통과해 수정 중 |
| `testing` | 정책 검사 후 저장소 하네스 실행 중 |
| `ready` | 수정 결과 검증 통과, push 대기 |
| `rejected` | 오탐 또는 수정 결과 검증 실패 |
| `failed` | 명령, 테스트, 정책 또는 HEAD 검사 실패 |
| `pushed` | 설정된 remote로 push 완료 |
| `completed` | direct 반영 또는 PR 생성 완료 |

`precheck_status`와 `precheck_reason`은 수정 전 판정과 근거를 보관한다. `postcheck_status`와 `postcheck_reason`은 수정 결과 판정과 근거를 보관한다. `tests_json`에는 설정된 명령과 종료 코드, 제한한 stdout·stderr를 기록하고 `last_error`에는 직전 실패 원인을 남긴다.

`job_events`는 상태 전이, worktree 생성·제거, 원격 이동, merge와 충돌 파일, 해결 사유, 재검증과 push 결과를 append-only로 기록한다. 전역 증가 `id`와 `--after-id` 조회는 외부 소비자와 Discord 전달 순서를 확인할 때 쓴다. Discord 전송 위치는 저장소별 `discord_cursors`에 따로 기록하므로 알림 장애가 작업 상태나 리뷰 입력 처리를 막지 않는다.

## 저장소별 규칙과 예외

`[[repositories]]`에서 대상 저장소와 하네스를 지정한다.

- `remote`, `target_branch`: 최신 기준을 fetch하고 결과를 push할 대상
- `publish_mode`: `direct` 또는 `pull_request`
- `local_path`: fetch에 사용할 로컬 저장소. 경로가 없으면 `--no-checkout` clone 생성
- `additional_instructions`: 대상 `AGENTS.md`에 덧붙일 지침
- `commit_message_template`: `{fingerprint}`, `{fingerprint_short}`, `{file}`을 사용할 수 있는 commit 형식
- `test_commands`: shell을 거치지 않고 실행할 argument 배열
- `command_timeout_seconds`, `max_attempts`: 명령 제한 시간과 작업 시도 횟수
- `max_remote_merge_attempts`: 처리 중 원격 이동을 merge·재검증할 최대 횟수

`[repositories.policy]`는 자동 처리 범위를 제한한다.

- `allowed_severities`
- `allowed_paths`, `denied_paths`
- `skipped_paths`, `skipped_fingerprints`
- `max_changed_files`, `max_changed_lines`
- `allow_new_files`, `allow_deletions`
- `require_finding_file_changed`

설정값과 리뷰 이벤트에 들어 있는 문자열을 shell 명령으로 실행하지 않는다. `direct`는 target branch에 commit을 바로 push하므로 branch protection과 token 권한이 허용해야 한다. token 격리, 정책·하네스·재검증과 worktree 분리는 반영 방식과 무관하게 적용한다.

## 자동 리뷰 연동 조건

`code-review-agent` 자동 전송은 아직 구성하지 않았다. 자동 트리거를 붙일 때 송신 측은 다음 조건을 지켜야 한다.

- 오탐 검증을 통과한 finding이 있을 때만 이벤트 전송
- PASS와 변경 없음 결과는 전송하지 않음
- Discord 알림과 리뷰 체크포인트를 수정 에이전트 장애와 분리
- 같은 target 재전송에도 동일한 fingerprint 사용
- 같은 장비에서는 `fix-agent submit`을 우선 사용하고, HTTP가 필요할 때만 Bearer token 사용
- Bearer token과 GitHub token을 설정 파일이나 이벤트에 직접 저장하지 않음
- `202 Accepted` 또는 CLI 등록 성공을 수정 완료로 해석하지 않음

이 작업은 `code-review-agent` 수정이 필요하다. 변경 전에 필요성, 대상 파일, 동작 영향과 검증 방법을 설명하고 사용자 승인을 받아야 한다.
