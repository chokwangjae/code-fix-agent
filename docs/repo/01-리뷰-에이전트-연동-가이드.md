# 리뷰 에이전트 연동 가이드

## 현재 상태

`code-fix-agent`는 HTTP API와 JSON 파일로 리뷰 이벤트를 받는다. `code-review-agent`에는 자동 전송 기능을 연결하지 않았다. 다른 저장소를 변경해야 하는 자동 연동 작업은 대상 파일과 영향을 설명하고 사용자 승인을 받은 뒤 진행한다.

현재 사용할 수 있는 방식은 두 가지다.

- `fix-agent submit`: 같은 장비의 리뷰 도구가 JSON 파일을 직접 등록. 수신 token 불필요
- `POST /reviews`: 다른 프로세스나 장비에서 Bearer token으로 이벤트 전송

두 입력은 같은 SQLite 작업 큐와 수정 절차를 사용한다.

실제 이벤트를 등록하면 `review_batch` 저장소는 한 리뷰의 finding을 최신 원격 target 기준 worktree 하나에서 처리한다. 검증과 하네스는 배치로 공유하되 commit과 push는 finding 변경 그룹별로 나눈다. 개발·검증 환경에서는 사용자가 대상 저장소 실행을 승인한 뒤 이벤트를 등록한다.

## 설치와 설정

```bash
cd /Users/brokenclaw/hermes-workspace/code-fix-agent
python3 -m venv .venv
.venv/bin/python -m pip install -e .
```

저장소에 포함된 `fix-agent.toml`은 다음 대상을 등록한다.

| ID | GitHub 저장소 | remote/target | 반영·처리 방식 |
|---|---|---|---|
| `matrix-mobile-v2` | `inswave/Matrix_Mobile_V2` | `origin/dev` | direct·review_batch |
| `testsquare-fable` | `inswave/TestSquare-Fable` | `origin/dev` | direct·review_batch |

다른 대상을 추가할 때는 `fix-agent.example.toml`을 복사한다.

```bash
cp fix-agent.example.toml fix-agent.local.toml
chmod 600 fix-agent.local.toml
```

인증값은 TOML에 직접 적거나 환경 변수로 받을 수 있다. 환경 변수 방식은 다음과 같다.

```bash
export CODE_FIX_TOKEN='replace-with-a-secret'
export MATRIX_MOBILE_FIX_GITHUB_TOKEN='repository-scoped-token'
export TESTSQUARE_FABLE_FIX_GITHUB_TOKEN='repository-scoped-token'

.venv/bin/fix-agent serve --config fix-agent.toml
```

TOML 직접 설정을 쓰면 다음 키로 바꾸고 대응하는 `*_env` 키를 제거한다.

```toml
[server]
host = "127.0.0.1"
port = 7081
token = "64자-난수-공유-비밀값"

[[repositories]]
id = "matrix-mobile-v2"
# 나머지 저장소 설정 생략
github_token = "repository-scoped-github-token"
```

| 용도 | TOML 직접값 | 환경 변수 이름 키 |
|---|---|---|
| HTTP 수신 인증 | `server.token` | `server.token_env` |
| GitHub clone·fetch·push·PR | `repositories.github_token` | `repositories.github_token_env` |

HTTP 수신 인증은 직접값과 환경 변수 이름 중 하나만 필수다. 둘 다 있거나 둘 다 없으면 설정 로드를 중단한다. GitHub 인증은 `github_token`과 `github_token_env`를 함께 설정할 수 없지만, 둘 다 생략하면 PC의 `gh auth`를 사용한다.

GitHub token은 대상 저장소 clone·fetch·push와 PR 방식의 PR 생성에 필요한 범위만 부여한다. Codex와 테스트 명령에서는 token, secret, password와 webhook 환경 변수를 제거하며 Git network 명령과 `gh pr` 명령에만 저장소 token을 전달한다.

`CODE_FIX_TOKEN`은 GitHub에서 발급받는 token이 아니다. HTTP 송신자와 fix agent가 같은 값을 사용하기만 하면 된다. 구현은 비어 있지 않은 임의 문자열을 받지만, 운영 값은 다음과 같이 32 bytes 난수로 만든다.

```bash
openssl rand -hex 32
```

결과 64자를 `server.token`에 적거나 `server.token_env`가 가리키는 환경 변수에 넣는다. 같은 장비에서 `fix-agent submit`만 호출하면 이 token이 필요 없다. `serve`를 실행하는 LaunchAgent에서는 필수다.

저장소별 GitHub 인증은 다음 순서로 결정한다.

1. `github_token` TOML 직접값
2. `github_token_env`가 가리키는 환경 변수의 실제 값
3. `gh auth token --hostname github.com`이 반환하는 PC 로그인 token

따라서 `gh auth login --hostname github.com`을 완료한 PC에서는 GitHub token을 TOML이나 환경 변수에 따로 적지 않아도 된다. 자동 인증은 GitHub 전용이며 `CODE_FIX_TOKEN`을 대신하지 않는다. `gh auth token` 실행시에는 다른 token·webhook 환경 변수를 제거하고, 받은 값은 Git network·PR 명령에만 전달한다.

TOML 직접값은 편리하지만 파일을 읽으면 token도 바로 확인할 수 있다. 직접값을 쓰는 경우 Git에서 제외된 `fix-agent.local.toml`을 사용하고 `chmod 600 fix-agent.local.toml`로 권한을 제한한다. 실제 token이 든 `fix-agent.toml`은 commit·push하지 않는다.

## Discord 작업 알림

웹훅 주소는 저장소별 `[repositories.discord]`에서 지정한다. 알림을 받을 저장소는 `enabled = true`로 설정하고, 발송을 중지할 때는 `false`로 바꾼다.

```toml
[repositories.discord]
enabled = true
webhook_url_env = "MATRIX_MOBILE_FIX_DISCORD_WEBHOOK_URL"
timeout_seconds = 30
```

`webhook_url_env`는 주소가 아니라 주소를 담을 환경 변수 이름이다. 실제 값은 프로세스를 시작하는 shell에 넣는다.

```bash
export MATRIX_MOBILE_FIX_DISCORD_WEBHOOK_URL='https://discord.com/api/webhooks/...'
export TESTSQUARE_FABLE_FIX_DISCORD_WEBHOOK_URL='https://discord.com/api/webhooks/...'
```

주소를 TOML에 직접 저장하는 방식은 다음과 같다.

```toml
[repositories.discord]
enabled = true
webhook_url = "https://discord.com/api/webhooks/..."
timeout_seconds = 30
```

직접 주소를 쓰면 `webhook_url_env`를 제거한다. 반대로 환경 변수 방식을 쓰면 `webhook_url`을 제거한다. 어느 방식이든 `enabled = true`가 아니면 발송하지 않는다.

Discord 기본 웹훅에는 별도 token이 필요 없다. Discord 호환 중계 서버가 Bearer 인증을 요구할 때만 `webhook_token_env = "..."`를 추가하고 그 환경 변수를 설정한다. `webhook_url = "https://..."`로 주소를 직접 적을 수도 있지만, 비밀값이 설정 파일과 Git 기록에 남을 수 있으므로 환경 변수 방식을 권장한다. `webhook_url`과 `webhook_url_env`를 함께 쓰면 설정 오류로 중단한다.

설정은 프로세스 시작 시 로드한다. `enabled`, `webhook_url`, `webhook_url_env`, `webhook_token_env`, `timeout_seconds`를 바꾼 후에는 아래 중 현재 실행 방식에 맞는 절차를 따른다.

- 직접 실행: 기존 `fix-agent serve`를 `Ctrl+C`로 종료한 뒤 같은 `--config` 경로로 다시 실행
- LaunchAgent: 필요한 환경 변수를 설정한 shell에서 `fix-agent-launchd --install` 재실행

실행 중인 프로세스가 없다면 재시작할 대상도 없다. 이 경우에는 token을 준비한 뒤 `serve`를 시작하거나 LaunchAgent를 설치한다.

알림 대상은 finding·배치 검증 시작과 완료, 수정 시작, 결과 검증 시작과 완료, 같은 worktree의 보완, 문제 finding 분리, 프로세스 재시도 예정, 정책 제외, target 이동, merge 충돌 감지·해결, push 완료, worktree 정리 실패와 작업의 `completed`·`rejected`·최종 `failed` 상태다. 재시도할 실패는 최종 실패 대신 재시도 예정으로 알린다. 검증과 수정 단계 알림은 이벤트를 기록한 직후 전송을 시도한다. 나머지 내부 진행 이벤트는 커서만 넘긴다. 웹훅 실패는 수정 작업 상태를 바꾸지 않는다. 실패 event ID, 횟수, 원인과 다음 재시도 시각을 `discord_cursors`에 남기고 5초, 30초, 2분, 10분 간격으로 재시도한다.

worker가 실행 중이면 재시도도 자동으로 처리한다. 직접 확인하거나 저장된 대기 시간을 무시하고 다시 보낼 때는 다음 명령을 쓴다.

```bash
.venv/bin/fix-agent notify-once --config fix-agent.toml
.venv/bin/fix-agent notify-once --config fix-agent.toml --force
```

처음 알림을 활성화하면 기존 event의 마지막 ID에 커서를 맞춰 과거 알림을 한꺼번에 보내지 않는다. 이후 생성된 event는 HTTP 2xx 응답을 받은 뒤에만 커서를 전진한다. 전송이 실제로 성공했지만 응답 확인에 실패한 경우 같은 event가 다시 갈 수 있으므로 Discord embed의 `Event ID`로 중복을 확인한다.

## 리뷰 이벤트 계약

`POST /reviews` 요청은 `Content-Type: application/json`을 사용하며 `Authorization: Bearer <CODE_FIX_TOKEN>`이 필요하다. 본문 형식은 `version = 1`이다.

필드 제약, fingerprint 생성법, 성공·오류 응답, 재시도와 버전 호환 규칙은 [리뷰 이벤트 v1 계약](02-리뷰-이벤트-v1-계약.md)을 기준으로 삼는다.

```json
{
  "version": 1,
  "repository": "inswave/Matrix_Mobile_V2",
  "branch": "dev",
  "baseline": "0123456789abcdef0123456789abcdef01234567",
  "target": "123456789abcdef0123456789abcdef012345678",
  "findings": [
    {
      "fingerprint": "sha256:54e4c2451c58e7dd7132565aa3f2153884e53b3c89aed1f54e63136b40c787b2",
      "severity": "Major",
      "commit": "123456789abcdef0123456789abcdef012345678",
      "file": "client/example/File.kt",
      "line": 42,
      "cause": "구체적인 실패 조건과 영향",
      "solution": "검증 가능한 수정 방법"
    }
  ]
}
```

각 commit ID는 40자리 또는 64자리 전체 object ID여야 한다. `file`은 저장소 상대 경로를 사용하고 `fingerprint`는 `sha256:` 뒤에 64자리 소문자 16진수를 붙인다. 하나의 이벤트에 finding을 한 개 이상 넣어야 한다.

`review_batch`의 worktree 수는 요청 수를 기준으로 정한다. 한 프로젝트·branch·review target에서 이슈가 10개 나왔다면 요청 하나의 `findings[]`에 10개를 넣는다. 그러면 worktree 하나에서 처리한다. 요청을 10건으로 나누면 배치와 worktree도 최대 10개가 된다. 송신기는 한 번의 리뷰 결과를 finding별 요청으로 분해하지 않는다.

HTTP 전송 예시는 다음과 같다.

```bash
curl --request POST http://127.0.0.1:7081/reviews \
  --header "Authorization: Bearer ${CODE_FIX_TOKEN}" \
  --header 'Content-Type: application/json' \
  --data @review-event.json
```

서버는 계약과 저장소 allowlist를 확인한 뒤 `202 Accepted`를 반환한다. 같은 저장소·branch·fingerprint 조합은 다시 등록하지 않는다.

## JSON 파일 직접 등록

서버와 수신 token 없이 이벤트를 큐에 넣고 작업 한 건을 처리할 수 있다. 송신 프로젝트는 설치된 `fix-agent` 실행 파일, 이 프로젝트의 설정 파일, 자신이 생성한 이벤트 파일만 사용한다. `code-fix-agent` 저장소 파일을 직접 수정하지 않는다.

```bash
.venv/bin/fix-agent submit \
  --config fix-agent.toml \
  --file review-event.json \
  --run-now
```

등록과 실행을 나누려면 `--run-now`를 생략한 뒤 다음 명령을 사용한다.

```bash
.venv/bin/fix-agent run-once --config fix-agent.toml
```

`--run-now`와 `run-once`는 호출할 때마다 대기 실행 단위를 최대 하나 처리한다. 실행 단위는 저장소 설정에 따라 리뷰 배치 하나 또는 finding 하나다. 상시 `serve`는 `[server].max_concurrent_jobs`에 지정한 수만큼 서로 다른 실행 단위를 처리하며 운영 예시값은 `3`이다. 상시 worker를 실행하지 않는다면 `no queued jobs`가 나올 때까지 `run-once`를 반복한다.

## 처리 절차

1. 저장소, branch, severity, fingerprint와 finding 경로를 정책으로 검사한다.
2. `local_path`가 없으면 GitHub 저장소를 `--no-checkout`으로 clone한다. 있으면 기존 Git 저장소를 사용한다.
3. `remote/target_branch`를 fetch하고 최신 commit을 구한다. 리뷰의 `target`이 최신 target의 조상이 아니면 중단한다.
4. 최신 target에서 detached worktree를 만들고 관리 경로의 소유자 권한과 실제 쓰기 가능 여부를 확인한다. 도입 commit과 finding line이 `baseline..target` 변경에 속하는지도 검사한다.
5. 전용 runtime cache를 사용하는 `setup_commands`로 해당 worktree의 의존성과 실행 환경을 준비한다. 실패한 명령은 같은 worktree에서 재시도한다.
6. read-only Codex가 배치의 실제 실패 경로를 한 번에 확인하고 fingerprint별 `precheck_reason`을 기록한다. 오탐만 개별 `rejected`로 제외한다.
7. 유효한 finding을 한 worktree에서 함께 수정한다. 같은 파일 finding은 한 변경 그룹으로 합치고 지원 파일도 한 그룹에만 배정한다.
8. 의존성 선언이 바뀌면 준비 명령을 다시 실행한 뒤 변경 정책, 저장소 하네스와 read-only 수정 결과 검증을 배치 전체에 적용한다. 결과와 사유는 fingerprint별로 기록한다.
9. 배치 검증이 반복해서 실패하면 원인 변경 그룹을 분리해 `finding` 처리 대기열로 돌리고, 나머지 변경은 같은 worktree에서 계속한다.
10. 검증된 변경을 그룹별 commit으로 나눈 뒤 원격 target을 다시 fetch한다.
11. 원격이 이동했으면 최신 target을 merge하고 충돌 해결 사유를 남긴 뒤 배치 전체 하네스와 결과 검증을 다시 실행한다.
12. 각 commit을 `remote/target_branch`로 순서대로 push한다. push 사이에 target이 이동해도 11단계부터 반복한다.
13. 모든 push 뒤 worktree를 강제 제거하고 임시 디렉터리 삭제와 `git worktree prune`을 수행한다.
14. 배치별 Codex 호출 수, token 사용량과 누적 실행 시간을 `batch_runs`에 기록한다.

`review_batch`에서는 리뷰 이벤트 하나가 worktree와 공유 검증의 단위이고, 같은 파일 finding 묶음이 commit과 push의 단위다. `processing_mode = "finding"` 저장소는 기존처럼 finding마다 독립 worktree를 사용한다. 상세 명령과 정리 조건은 [수정 작업과 worktree 생명주기](03-수정-작업과-worktree-생명주기.md)에 정리했다.

## 상태와 판단 기록

상태는 `state_dir/jobs.db`에 저장한다.

```bash
.venv/bin/fix-agent jobs --config fix-agent.toml --json
.venv/bin/fix-agent events --config fix-agent.toml --job-id 41 --json
.venv/bin/fix-agent events --config fix-agent.toml --after-id 120 --json
```

| 상태 | 의미 |
|---|---|
| `skipped` | severity, 경로 또는 fingerprint 예외로 처리 제외 |
| `queued` | 처리 대기 |
| `validating` | finding 사실 여부 확인 중 |
| `fixing` | 사실 검증을 통과해 수정 중 |
| `testing` | 정책 검사 후 저장소 하네스 실행 중 |
| `ready` | 수정 결과 검증 통과, push 대기 |
| `rejected` | 독립 사실 검증에서 오탐으로 판정 |
| `failed` | 명령, 테스트, 정책, 결과 검증 또는 HEAD 검사 실패. 설정에 따라 재시도 대기 포함 |
| `pushed` | 설정된 remote로 push 완료 |
| `completed` | direct 반영 또는 PR 생성 완료 |

`precheck_status`와 `precheck_reason`은 수정 전 판정과 근거를 보관한다. `postcheck_status`와 `postcheck_reason`은 수정 결과 판정과 근거를 보관한다. `tests_json`에는 설정된 명령과 종료 코드, 제한한 stdout·stderr를 기록한다. `last_error`에는 직전 실패 원인, `next_attempt_at`에는 다음 시도 시각을 남긴다.

`batch_runs`는 배치 ID, 상태, 시도 횟수, Codex 호출 수, 입력·cache·출력·reasoning·전체 token과 누적 실행 시간을 보관한다. HTTP·CLI 접수 응답의 `batch_id`로 리뷰 이벤트와 이 기록을 연결한다. `processing_mode = "finding"` 응답의 `batch_id`는 `null`이다.

`job_events`는 상태 전이, worktree 생성·제거, 권한 확인·복구, 원격 이동, merge와 충돌 파일, 해결 사유, 재검증과 push 결과를 append-only로 기록한다. `worktree_permissions_ready`에는 생성 직후 검사 수와 전용 cache 경로, `worktree_permissions_repaired`에는 작업 중 복구한 파일·디렉터리 수와 실행 단계를 남긴다. 전역 증가 `id`와 `--after-id` 조회는 외부 소비자와 Discord 전달 순서를 확인할 때 쓴다. Discord 전송 위치는 저장소별 `discord_cursors`에 따로 기록하므로 알림 장애가 작업 상태나 리뷰 입력 처리를 막지 않는다.

## 저장소별 규칙과 예외

`[[repositories]]`에서 대상 저장소와 하네스를 지정한다.

- `remote`, `target_branch`: 최신 기준을 fetch하고 결과를 push할 대상
- `publish_mode`: `direct` 또는 `pull_request`
- `processing_mode`: `review_batch` 또는 기존 `finding`. `review_batch`는 `publish_mode = "direct"`와 함께 사용
- `local_path`: fetch에 사용할 로컬 저장소. 경로가 없으면 `--no-checkout` clone 생성
- `additional_instructions`: 대상 `AGENTS.md`에 덧붙일 지침
- `commit_message_template`: 첫 줄의 `{title}`과 본문에서 `{fingerprint}`, `{fingerprint_short}`, `{file}`을 사용할 수 있는 commit 형식. `{title}`은 검증된 diff와 대상 저장소 규칙으로 생성하며, 기존 template에 `{title}`이 없으면 첫 줄을 생성 제목으로 교체
- `git_author_name`, `git_author_email`: 자동 생성 commit과 원격 merge commit의 작성자
- `setup_commands`: worktree에서 Codex와 하네스보다 먼저 실행할 환경 준비 argument 배열
- `setup_watch_paths`: 내용이 바뀌면 준비 명령을 다시 실행할 저장소 상대 경로 패턴
- `test_commands`: shell을 거치지 않고 실행할 argument 배열
- `command_timeout_seconds`: 명령 제한 시간
- `setup_max_attempts`: 준비 명령을 같은 worktree에서 실행할 최대 횟수
- `setup_retry_delay_seconds`: 준비 명령 재시도 간격
- `max_attempts`: 전체 시도 횟수. `0`이면 성공할 때까지 횟수 제한 없이 재시도
- `retry_delay_seconds`: 프로세스 오류 뒤 같은 job을 새 worktree에서 다시 시작할 때까지의 대기 시간
- `max_remote_merge_attempts`: 처리 중 원격 이동을 merge·재검증할 최대 횟수

동시 작업 수는 저장소별 실행 설정이 아니라 서버 전체 설정이다.

```toml
[server]
max_concurrent_jobs = 3
```

각 worker는 리뷰 배치나 finding 하나가 push와 worktree 정리를 끝낼 때까지 해당 실행 단위를 맡는다. 같은 저장소의 다른 worker가 먼저 target을 갱신하면 뒤 worker는 자기 worktree에서 최신 target을 merge하고 전체 검증을 다시 실행한다.

`[repositories.policy]`는 자동 처리 범위를 제한한다.

- `allowed_severities`
- `allowed_paths`, `denied_paths`
- `skipped_paths`, `skipped_fingerprints`
- `max_changed_files`, `max_changed_lines`: `0`이면 변경량 무제한. 운영 설정은 둘 다 `0`
- `allow_new_files`, `allow_deletions`: 허용 경로 안의 파일 추가·삭제 허용 여부. 운영 설정은 둘 다 `true`
- `require_finding_file_changed`

기본 `denied_paths`는 `.github/workflows/**`, `.env*`, `**/.env*`, `**/*.p12`, `**/*.mobileprovision`이다. 저장소 루트와 하위 디렉터리의 환경 파일, 인증서·프로비저닝 프로파일과 GitHub Actions workflow 수정을 막는다. 저장소별 TOML에서 목록을 바꿀 수 있다.

설정값과 리뷰 이벤트에 들어 있는 문자열을 shell 명령으로 실행하지 않는다. `direct`는 target branch에 commit을 바로 push하므로 branch protection과 token 권한이 허용해야 한다. token 격리, 정책·하네스·재검증과 worktree 분리는 반영 방식과 무관하게 적용한다.

준비 명령도 `test_commands`와 같은 제한 시간과 비밀값 제거 환경을 사용한다. 초기 준비와 `setup_watch_paths` 변경 뒤 준비가 끝나야 Codex 검증 또는 하네스를 시작한다. 각 실패의 command, 종료 코드와 제한한 stdout·stderr는 `environment_setup_failed` event에 남는다. 준비 명령이 tracked 파일이나 Git이 추적할 새 파일을 만들면 실행 전 내용을 복원한다. 복원 뒤 diff가 준비 전과 다르면 수정분과 분리할 수 없으므로 작업을 실패 처리한다.

## 자동 리뷰 연동 조건

`code-review-agent` 자동 전송은 아직 구성하지 않았다. 자동 트리거를 붙일 때 송신 측은 다음 조건을 지켜야 한다.

- 오탐 검증을 통과한 finding이 있을 때만 이벤트 전송
- PASS와 변경 없음 결과는 전송하지 않음
- Discord 알림과 리뷰 체크포인트를 수정 에이전트 장애와 분리
- 같은 target 재전송에도 동일한 fingerprint 사용
- 같은 장비에서는 `fix-agent submit`을 우선 사용하고, HTTP가 필요할 때만 Bearer token 사용
- Bearer token과 GitHub token을 리뷰 이벤트에 저장하지 않음. TOML 직접값은 Git에서 제외된 로컬 설정에만 저장
- `202 Accepted` 또는 CLI 등록 성공을 수정 완료로 해석하지 않음

이 작업은 `code-review-agent` 수정이 필요하다. 변경 전에 필요성, 대상 파일, 동작 영향과 검증 방법을 설명하고 사용자 승인을 받아야 한다.
