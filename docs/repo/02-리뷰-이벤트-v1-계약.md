# 리뷰 이벤트 v1 계약

이 문서는 외부 리뷰 도구가 `code-fix-agent`에 리뷰 결과를 전달할 때 구현해야 할 계약을 정한다. 운영 설치와 작업 처리 절차는 [리뷰 에이전트 연동 가이드](01-리뷰-에이전트-연동-가이드.md)를 함께 확인한다.

## 전송 방식 선택

| 조건 | 권장 방식 | 수신 인증 |
|---|---|---|
| 같은 장비에서 두 프로젝트 실행 | `fix-agent submit` | 불필요 |
| 분리된 프로세스에서 HTTP 사용 | `POST /reviews` | Bearer token 필수 |
| 다른 장비나 네트워크에서 전송 | HTTPS reverse proxy 뒤의 `POST /reviews` | Bearer token 필수 |

로컬 방식은 리뷰 도구가 이벤트 JSON 파일을 만든 뒤 설치된 CLI를 실행한다.

```bash
/absolute/path/to/code-fix-agent/.venv/bin/fix-agent submit \
  --config /absolute/path/to/code-fix-agent/fix-agent.toml \
  --file /absolute/path/to/review-event.json \
  --run-now
```

이 경로에는 `CODE_FIX_TOKEN`이 필요 없다. `--run-now`는 대기 실행 단위를 최대 하나 처리한다. `review_batch` 저장소에서는 리뷰 이벤트 배치 하나, `finding` 저장소에서는 finding 하나가 실행 단위다. 여러 작업을 모두 처리하려면 `fix-agent run-once`를 `no queued jobs`가 나올 때까지 호출하거나 상시 worker가 포함된 `fix-agent serve`를 사용한다. `serve`의 동시 처리 수는 `[server].max_concurrent_jobs`이며 운영 예시값은 `3`이다.

수신 인증과 GitHub 인증은 용도가 다르다.

- `server.token` 또는 `server.token_env`가 가리키는 값: HTTP `/reviews` 호출자 인증. 로컬 CLI에서는 사용하지 않음
- GitHub 인증: `github_token`, `github_token_env`의 실제 값, PC의 `gh auth` 순으로 선택. 저장소 clone·fetch·push와 선택적인 PR 생성에 사용

GitHub target branch나 PR branch에 push하려면 인증 자체를 없앨 수 없다. 명시적 token이 없으면 worker가 `gh auth token --hostname github.com`으로 PC 로그인 token을 읽어 Git push와 PR 명령에 사용한다. SSH key는 사용하지 않는다.

## HTTP 요청

```http
POST /reviews HTTP/1.1
Host: 127.0.0.1:7081
Authorization: Bearer <CODE_FIX_TOKEN>
Content-Type: application/json
Content-Length: <UTF-8 본문 byte 수>
```

- 기본 주소: `http://127.0.0.1:7081/reviews`
- 기본 최대 본문: 1,048,576 bytes. `server.max_body_bytes`로 변경 가능
- 문자 인코딩: UTF-8
- 응답 형식: `application/json; charset=utf-8`
- `Idempotency-Key` header는 사용하지 않는다. finding fingerprint가 중복 방지 key다.

내장 서버는 TLS를 제공하지 않는다. 같은 장비에서는 loopback 주소를 유지한다. 다른 장비에서 호출하려면 HTTPS reverse proxy와 방화벽 또는 source IP 제한을 두고, 내장 서버를 인터넷에 직접 노출하지 않는다.

## 이벤트 구조

```json
{
  "version": 1,
  "repository": "inswave/Matrix_Mobile_V2",
  "branch": "dev",
  "baseline": "0123456789abcdef0123456789abcdef01234567",
  "target": "123456789abcdef0123456789abcdef012345678",
  "findings": [
    {
      "fingerprint": "sha256:54e4c2451c58e7dd7132565aa3f2153884e53b3c89aed1f54e63136b40c787b2",
      "severity": "Major",
      "commit": "123456789abcdef0123456789abcdef012345678",
      "file": "client/example/File.kt",
      "line": 42,
      "cause": "구체적인 실패 조건과 영향",
      "solution": "검증 가능한 수정 방법"
    }
  ]
}
```

### 최상위 필드

| 필드 | 형식 | 규칙 |
|---|---|---|
| `version` | number | 정수 `1`만 허용 |
| `repository` | string | 설정의 `owner/repository`와 같은 표기 사용 |
| `branch` | string | 설정의 `target_branch`와 정확히 일치 |
| `baseline` | string | 40자리 또는 64자리 전체 Git object ID |
| `target` | string | 40자리 또는 64자리 전체 Git object ID |
| `findings` | array | 한 개 이상의 finding 필요 |

`repository` 조회는 대소문자를 구분하지 않지만 중복 기록의 일관성을 위해 설정에 적힌 표기를 그대로 보내야 한다. `branch`는 대소문자를 구분하며 수신 저장소 설정의 `target_branch`를 뜻한다. 송신기가 Git remote나 반영 방식을 선택하지는 않는다. 수신 측 `remote`, `target_branch`, `publish_mode` 설정이 실제 반영 위치를 결정한다. `baseline`과 `target`에는 축약 SHA를 보내지 않는다.

같은 repository·branch·baseline·target에서 나온 finding은 요청 하나의 `findings[]`에 모은다. `review_batch`는 HTTP 요청 또는 CLI 제출 한 건을 배치 하나로 만들기 때문에 finding별로 요청을 나누면 공유 worktree와 공유 검증 효과가 사라진다.

### finding 필드

| 필드 | 형식 | 규칙 |
|---|---|---|
| `fingerprint` | string | `sha256:`와 소문자 16진수 64자리 |
| `severity` | string | `Critical`, `Major`, `Minor` 중 하나 |
| `commit` | string | finding 도입 commit의 40자리 또는 64자리 전체 object ID |
| `file` | string | 저장소 기준 POSIX 상대 경로. 절대 경로와 `..` 금지 |
| `line` | number | 1 이상의 정수. boolean 금지 |
| `cause` | string | 공백 제거 후 비어 있지 않아야 하며 최대 20,000자 |
| `solution` | string | 공백 제거 후 비어 있지 않아야 하며 최대 20,000자 |

한 이벤트 안에서 fingerprint가 중복되면 이벤트 전체를 거부한다. 계약에 없는 요청 필드는 현재 무시되지만 송신 측은 이에 의존하지 말고 위 필드만 보내야 한다.

## fingerprint 생성

수신기는 fingerprint 형식만 검사하고 원문으로 hash를 다시 계산하지 않는다. 송신기는 같은 논리적 finding을 다시 보낼 때 같은 값을 사용해야 한다. 서로 다른 finding에는 서로 다른 값을 써야 한다.

권장 canonical 입력은 다음 순서의 JSON array다.

```text
[
  repository.casefold(),
  branch,
  commit.lower(),
  file,
  line,
  collapse_whitespace(cause)
]
```

공백 축약은 `cause` 앞뒤 공백을 제거하고 연속된 Unicode 공백을 ASCII space 하나로 바꾼다. JSON은 UTF-8, compact separator, 문자열 원문 보존 방식으로 직렬화한다. 그 byte 배열의 SHA-256 앞에 `sha256:`를 붙인다.

Python 구현 예시는 다음과 같다.

```python
from hashlib import sha256
import json


def finding_fingerprint(repository, branch, commit, file, line, cause):
    canonical = json.dumps(
        [
            repository.casefold(),
            branch,
            commit.lower(),
            file,
            line,
            " ".join(cause.split()),
        ],
        ensure_ascii=False,
        separators=(",", ":"),
    ).encode("utf-8")
    return "sha256:" + sha256(canonical).hexdigest()
```

문서 예시의 검증 vector는 다음과 같다.

```text
canonical JSON:
["inswave/matrix_mobile_v2","dev","123456789abcdef0123456789abcdef012345678","client/example/File.kt",42,"구체적인 실패 조건과 영향"]

fingerprint:
sha256:54e4c2451c58e7dd7132565aa3f2153884e53b3c89aed1f54e63136b40c787b2
```

중복 판단 범위는 `repository + branch + fingerprint`다. target이 바뀌어도 이 조합이 같으면 기존 작업으로 처리한다. 같은 문제를 새 target에서 다시 수정해야 한다면 검토 결과가 정말 별도 작업인지 판단한 뒤 fingerprint 정책을 정해야 한다.

## 접수 응답

HTTP 성공은 `202 Accepted`다. CLI 성공은 종료 코드 `0`과 같은 JSON을 stdout으로 반환한다.

```json
{
  "job_ids": [41, 42],
  "created": 2,
  "duplicate": 0,
  "skipped": 1,
  "batch_id": "35d79cb8cf834af79dd5718c3bffd519"
}
```

| 필드 | 의미 |
|---|---|
| `job_ids` | 새 작업과 기존 중복 작업을 포함한 로컬 SQLite ID |
| `created` | 이번 요청에서 처음 생성한 작업 수. `skipped` 포함 |
| `duplicate` | 기존 `repository + branch + fingerprint`와 일치한 수 |
| `skipped` | 이번에 생성됐지만 저장소 정책으로 처리 제외된 수 |
| `batch_id` | `review_batch`로 새 작업을 만든 요청의 배치 ID. `finding` 모드이거나 모두 중복이면 `null` |

`202`는 저장 또는 중복 확인이 끝났다는 뜻이다. 사실 검증, 수정, 테스트와 push 완료를 뜻하지 않는다. finding마다 SQLite job 하나가 생기며, `review_batch`는 이번 요청에서 새로 만든 job을 같은 배치로 묶는다.

## HTTP 오류와 송신 측 처리

| 상태 | 대표 응답 | 송신 측 처리 |
|---|---|---|
| `400` | `{"error":"invalid JSON"}` 또는 `invalid content length` | 본문 생성과 header 수정 후 재전송 |
| `401` | `{"error":"unauthorized"}` | token 설정 확인 후 재전송 |
| `404` | `{"error":"not found"}` | endpoint 경로 수정 |
| `413` | `{"error":"invalid body size"}` | 빈 본문 또는 크기 초과 수정 |
| `422` | `{"error":"<계약 또는 설정 오류>"}` | 필드, 버전, repository allowlist 수정 |

`400`, `401`, `404`, `413`, `422`는 같은 요청을 그대로 재시도해도 해결되지 않는다. 연결 실패, timeout, 응답을 받기 전 연결 종료나 예상하지 못한 `5xx`만 일시 오류로 취급한다.

## 재시도와 중복 처리

송신기는 at-least-once 전송을 사용해도 된다. 응답을 받지 못했다면 같은 fingerprint로 재시도한다. 수신기는 등록된 `repository + branch + fingerprint`를 다시 만들지 않고 기존 `job_id`를 반환한다.

권장 재시도 간격은 5초, 30초, 2분, 10분이며 이후에는 10분 상한을 둔다. 무한 재시도 대신 운영 경고와 최대 보관 시간을 정한다. HTTP 연결과 응답 timeout도 송신 측에서 설정한다.

- `202` 수신: 해당 전송 재시도 종료
- CLI 종료 코드 `0`: 해당 등록 재시도 종료
- HTTP `4xx` 또는 CLI 종료 코드 `1`: 원인 수정 전 자동 재시도 중단
- 연결 오류 또는 응답 불명: 같은 fingerprint로 재시도

## 비동기 처리와 결과 확인

접수 뒤 worker가 다음 항목을 별도로 검사한다.

- 이벤트 `target`이 현재 `remote/target_branch`의 조상인지 여부
- finding이 `baseline..target` 변경에 포함되는지 여부
- 독립적인 사실 검증과 판단 사유
- 대상 저장소 `AGENTS.md`, 추가 지침과 정책
- 대상 저장소 테스트 하네스
- 수정 결과 재검증과 판단 사유
- 작업 중 원격 이동에 대한 merge, 충돌 해결과 전체 재검증

worker는 작업을 시작할 때 최신 원격 target에서 detached worktree를 만든다. `review_batch`는 이벤트의 finding을 같은 worktree에서 검증·수정하고, 오탐만 fingerprint별 `rejected`로 제외한다. 같은 파일 finding은 한 변경 그룹으로 합치며 다른 그룹은 commit과 push를 나눈다. 작업 중 target이 이동하면 worktree에서 merge하고 배치 전체 하네스와 수정 결과 검증을 다시 실행한다. 반복 실패 원인이 특정 그룹이면 그 그룹만 기존 finding 처리 방식으로 전환한다.

현재 callback과 외부 상태 조회 API는 없다. 운영자는 다음 명령으로 상태와 순차 event log를 확인한다.

```bash
.venv/bin/fix-agent jobs --config fix-agent.toml --json
.venv/bin/fix-agent events --config fix-agent.toml --job-id 41 --json
.venv/bin/fix-agent events --config fix-agent.toml --after-id 120 --json
```

외부 송신기는 `job_ids`와 선택적인 `batch_id`를 로컬 상관관계 값으로 기록하되 완료 통지로 사용하지 않는다. `job_events.id`는 전역 증가하며 Discord 알림에도 Event ID로 포함된다. Discord 전달 checkpoint는 저장소별 `discord_cursors`가 관리한다. callback이나 상태 API가 필요하면 `code-fix-agent` 기능으로 먼저 추가하고 이 계약을 같은 커밋에서 갱신한다.

## 버전과 호환성

- 현재 수신 버전은 `1`뿐이다. 다른 값은 `422`다.
- 송신기는 응답에 추가된 알 수 없는 필드를 무시해야 한다.
- 송신기는 요청의 미정의 필드가 보존되거나 처리된다고 가정하지 않는다.
- 필드 제거, 의미 변경처럼 호환되지 않는 변경은 새 계약 버전으로 분리한다.
- v1 동작을 바꾸면 `README.md`, 연동 가이드와 이 문서를 같은 커밋에서 검토한다.

## 송신 구현 점검표

- 설정과 같은 `repository`, `branch` 사용
- 전체 Git object ID 사용
- 알려진 vector로 fingerprint 구현 검증
- 같은 finding 재전송 시 fingerprint 유지
- PASS 또는 finding 없는 이벤트 미전송
- HTTP token을 설정 파일, 이벤트, 로그에 기록하지 않음
- `202`를 수정 완료로 처리하지 않음
- `4xx`와 일시 오류의 재시도 정책 분리
- 이벤트와 응답의 `job_ids`, `batch_id`를 운영 로그에서 연결
